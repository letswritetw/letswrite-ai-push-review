# AI Code Review

審查一個 commit，或一個分支範圍（`base..head`）帶進來的改動。讀者是開發者本人和組長：報告會直接貼到 Gitea 的 PR 或 issue，所以每一條都要能讓人照著去改。

自動審查時沒有人可以回答問題，遇到不確定的地方寫進報告標「待確認」，不要停下來問。

## 規則

- **只讀不改**：不修改任何檔案。
- **工具**：讀檔用 Read，搜尋用 Grep／Glob，不要用 Bash 的 `cat`、`sed`、`grep`。Bash 只能跑 git 唯讀指令（`git show`、`git diff`、`git log`）和 `codegraph explore`。一次只跑一個指令，不要用 `cd`、`&&`、`|` 串接；自動審查時其他指令都會被拒絕。
- **範圍**：只審這次改到的程式，以及它影響到的既有功能。diff 以外的既有問題，除非被這次改動觸發或放大，否則不報。審的是分支範圍時，看的是最後的結果：前面 commit 寫錯、後面 commit 已經修好的，不報。
- **要有證據**：每一條都附檔案位置和有問題的程式碼。沒辦法從程式碼證實的，標「待確認」並說明缺什麼資訊。
- **不報**：排版、命名風格、個人偏好、「可以考慮」這類沒有具體風險的建議，這些交給靜態掃描工具（例如 SonarQube、ESLint）。重點放在掃描工具抓不到的地方：業務邏輯、權限判斷、跨功能影響。
- **格式固定**：不論使用者個人設定的輸出風格是什麼，一律照下面的格式，用繁體中文（台灣用語）。

## 步驟

1. **取得改動**：
   - 給的是一個 commit：`git show --stat <sha>` 看範圍，再 `git show <sha>` 看完整 diff。沒給就用 `HEAD`。
   - 給的是範圍 `base..head`：`git log --oneline --no-merges base..head` 看有哪些 commit，`git diff --stat base head` 看範圍，`git diff base head` 看整體 diff。分支中間合併過其他分支時，整體 diff 會混進別人的改動，這時改用 `git show <sha>` 逐一看列出的 commit。
2. **讀專案規則**：git 根目錄有 `.ai-review.md` 就讀進來，裡面寫的是這個專案特有的審查重點，優先度跟下面的清單相同。
3. **對照業務規則**：git 根目錄有 `docs/ai-rules/` 才做這一步，做法見下一節。
4. **確認上下文**：用 Read／Grep 讀改動附近的程式、呼叫端、被呼叫的函式，確認問題真的存在再報。
5. **逐項檢查並輸出**：依檢查清單逐項看過，照格式輸出。diff 很大時先看風險最高的檔案（資料存取、權限、對外 API、共用函式），並在結論說明哪些沒細看。

## 對照業務規則（避免改 A 壞 B）

`docs/ai-rules/*.md` 是專案預先寫好、給 AI 讀的業務規則。每個檔案是一個功能：
- frontmatter 的 `files` 列出這個功能用到的程式檔，`keywords` 列出相關名詞和函式名。
- 每條規則 `## <ID> 標題` 底下有 `when`（什麼情況）、`then`（系統應有的行為）、`code`（程式位置）、`evidence`（程式碼原文）、`status`。

**找出受影響的規則**：下面每一項都要做，查到的規則檔合起來一起看。
- **改到的檔案**：用每個改動檔案的路徑 grep `docs/ai-rules/`，對到 `files` 或 `code` 欄位。
- **改到的函式、預存程序、API action**：用名稱 grep `docs/ai-rules/`，對到 `code` 和 `keywords` 欄位。這一步會找到「別的功能也在用這段程式」的規則，是抓跨功能影響的關鍵。
- **改到的共用函式**：用 Grep 找它在專案裡的呼叫端，再用呼叫端的檔案路徑查規則檔。repo 有 `.codegraph/` 時，可以改用 `codegraph explore "<函式名>"` 看呼叫關係和影響範圍。

**逐條對照**：把改動後的程式套進每條相關規則的 `when`，檢查 `then` 是否還成立。
- **規則被破壞，而且看不出是刻意的**：報成「業務規則」類的發現，寫出規則 ID（例如 `ORDER-02`）和規則檔名。嚴重度依影響範圍判斷，另一個功能因此壞掉通常是 `high`。
- **commit 明顯是刻意改這個業務邏輯**（commit 訊息或改動內容說得通）：不算錯誤。報一條 `low`「業務規則」：規則檔需要更新，寫出要改哪一條規則。

**規則可信度**：
- `status: verified` 的規則可以當依據。
- `inferred`、`unverified` 只能當線索，以程式碼為準。
- 規則的 `verified_at` 到這次改動之前，`files` 裡的檔案已經有其他異動時（`git log <verified_at>..<base> -- <files>` 有輸出；審單一 commit 時 `<base>` 是 `<sha>~1`），規則可能已經過時，同樣只能當線索。

## 檢查清單

標籤對應的標準：
- `A01`～`A10`：[OWASP Top 10:2025](https://owasp.org/Top10/2025/)
- `CWE-`：[CWE Top 25 (2025)](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html)
- `ASVS V`：[OWASP ASVS 5.0](https://owasp.org/www-project-application-security-verification-standard/)

報告的「依據」欄填對得上的那個。

### 共通（依優先度）

1. **業務規則**：照上一節對照 `docs/ai-rules/`。
2. **正確性**：
   - 邏輯錯誤、條件寫反、邊界值、null／空值
   - 非同步沒等
   - 多個資料表的更新沒包在同一個交易裡，失敗時留下不一致的資料
3. **例外處理**（A10）：
   - 例外被吞掉
   - 失敗時反而放行（fail open）
   - 錯誤訊息把堆疊、SQL、內部路徑回傳給使用者
4. **效能**：
   - 迴圈內查資料庫或呼叫 API
   - 一次撈全部資料沒有分頁
   - 重複查詢相同的資料
5. **可維護性**：只報會造成實際風險的，例如同一段邏輯複製到多處，改一處漏一處。

### 後端（C#／.NET、SQL、Handler／API）

- **存取控制**（A01、CWE-862、CWE-639、ASVS V8）：
  - 新的 Handler、action、API 沒檢查登入和角色。
  - 用前端傳來的 ID（會員、訂單、門市代碼）存取資料時，沒確認這筆資料屬於目前使用者可以看的範圍。
  - 只靠前端隱藏按鈕擋權限。
- **注入**（A05、CWE-89、CWE-78）：
  - SQL 字串串接、未參數化的查詢。
  - 預存程序裡用 `EXEC` 串接動態 SQL。
  - 組命令列字串。
- **機敏資料**（A04）：
  - 寫死的密碼、API key、token、連線字串。
  - 身分證字號、手機、地址、Email 寫進 log、回傳給不需要的前端，或沒有遮罩就顯示。
- **設定**（A02）：
  - `Web.config` 開了 debug。
  - CORS 設成 `*`。
  - 關掉 TLS 憑證驗證（`ServerCertificateValidationCallback` 永遠回 true）。
- **外部輸入**（A08、CWE-22、CWE-434、CWE-502）：
  - 路徑穿越。
  - 檔案上傳沒檢查類型和大小。
  - 不安全的反序列化。
  - 下載並執行外部腳本。

### 前端（JavaScript、Vue、ASPX）

- **XSS**（A05、CWE-79、ASVS V3）：
  - 未編碼的資料塞進 `innerHTML`、`v-html`、jQuery `.html()`、`document.write`。
  - ASPX 用 `<%= %>` 輸出使用者資料（要用 `<%: %>` 或 `HttpUtility.HtmlEncode`）。
- **CSRF**（CWE-352）：
  - 會修改資料的請求用 GET。
  - 缺少 anti-forgery token。
- **權限**（A01）：功能只在前端隱藏，後端 API 沒擋。
- **機敏資料**：
  - 個資或 token 存進 `localStorage`，或放在 URL query string。
  - 用 `console.log` 印出個資。
- **供應鏈**（A03）：
  - 新加的 CDN script 沒鎖版本、沒有 SRI。
  - 新增來路不明的套件。
- **互動流程**：
  - 非同步請求沒處理錯誤。
  - 送出按鈕可以連點造成重複送出。

## 嚴重度

- `high`：上線就會出事，例如資安漏洞、資料毀損或外洩、主要流程或其他功能壞掉
- `medium`：特定情況才出錯、少了錯誤處理或權限檢查但還有其他防線、明顯的效能問題
- `low`：風險小，下次改到時順手處理即可；業務規則檔需要更新也算這級
- `none`：沒有發現問題

## 輸出格式

版面比照 PR-Agent 的「PR Code Suggestions」：用 HTML 表格分成三欄（分類、建議、影響），每條建議收合在 `<details>` 裡，點開才看到說明、檔案連結和修改建議。Gitea 的 PR 和 issue 都能正確顯示這種格式。

**開頭兩行**是給自動流程讀的 HTML 註解，在 Gitea 上看不到。前面不可以有任何文字：
- 第 1 行 `<!-- SEVERITY: <等級> -->`：等級取所有發現裡最高的一個，自動流程靠這行決定要不要通知。
- 第 2 行 `<!-- FINDINGS: <嚴重度>/<分類> ... -->`：每條發現各列一組，用空格隔開。自動流程靠這行決定 label。

分類只能從這五個裡選：`業務規則`、`資安`、`正確性`、`效能`、`可維護性`。

沒有發現問題時只輸出兩行：

~~~~
<!-- SEVERITY: none -->
未發現需要處理的問題。
~~~~

### 結論

<一兩句：整體風險、對照了哪些業務規則檔、哪些部分沒細看或標了待確認>
~~~~

**表格規則**：
- **列的順序**：同一個分類的建議放在一起；分類的順序依它裡面最嚴重的那條，由高到低。同一個分類裡，也依嚴重度由高到低。
- **分類格**：每個分類的第一列用 `<tr><td rowspan=N>分類</td>` 開頭，N 是這個分類的建議數。同一個分類後面的列只用 `<tr><td>` 開頭，不再寫分類格。
- **空行**：`<td>` 後面空三行再接 `<details>`，`<details>` 裡每一段之間都要空一行，`高`／`中`／`低` 後面也要空一行。少了空行，Gitea 會把裡面的 Markdown 當成純文字顯示。
- **影響欄**：只能寫 `高`、`中`、`低`，對應 high、medium、low。
- **依據**：沒有對應的業務規則或標準時，整段省略。

**分段**：一段只講一件事，段落之間空一行，不要把整條說明擠成一段。
- **問題**：第一段一句話講後果。成因、觸發方式或例子、影響範圍和嚴重度判斷，各自分段；內容少時可以合併，但一段不超過三句。
- **建議**：先寫最主要的改法。有兩種以上做法，或要先確認某件事再決定時，後面用清單列出，一項一種。

**程式碼與連結**：
- **程式碼**：超過一個名稱的程式碼一律放在程式碼區塊裡。有具體的改法就用 `diff` 區塊，`-` 是原本、`+` 是建議；沒有具體改法就用對應語言的區塊，放有問題的那幾行。
- **內文提到的名稱**：變數、函式、屬性、鍵名、檔名這類單一名稱，用行內反引號包起來，例如 `__proto__`、`Object.prototype`。沒包的話，`__proto__` 前後的底線會被當成粗體，畫面上只剩粗體的 proto。名稱本身含反引號時，改放程式碼區塊。`<summary>` 那一行不會轉換 Markdown，不要加反引號，直接寫名稱。
- **檔案連結**：
  - 提示裡有「檔案連結前綴」時，寫成 `[路徑 [起-迄]](<{前綴}/路徑#L起-L迄>)`，`{前綴}` 換成提示給的網址，只有一行就寫 `#L行號`。整個網址前後要用 `<` `>` 包起來，路徑有空格或中文時才不會斷掉。
  - 沒有前綴（手動執行時）就只寫 `路徑:起-迄`。
